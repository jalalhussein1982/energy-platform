# Assessment of `docs/overview/final-report.md`

25 September 2026. The original report is preserved unchanged. Line numbers refer to the reviewed copy recorded in `evidence/source-baseline.json`.

**I agree with the report's central account of what was built. I would not submit it unchanged.** It accurately describes a substantial platform, but compresses design intent, one-off demonstrations and recurring operational guarantees into stronger claims than the available evidence supports. These corrections matter to assignment acceptance; they are not a copy-editing exercise.

## Claims that stand

The shared Python library, immutable-raw/derived-data separation, explicit source contracts, manifest-driven targets, constrained contributor routes, PostgreSQL history, replay machinery, Helm/Terraform delivery and live deployment all have implementation behind them. The fresh results support the reported 928 offline tests, and separate PostgreSQL tests and the demo also passed.

The junior/agent workflow is a strong answer to the brief. Correctly stopping at admission is part of that success. SQL and private dashboards are sufficient interfaces for this assignment. The absence of a public website or an LLM in the operational ingestion path is not a shortcoming.

## Claims requiring substantive correction

| Report location | Assessment | Accurate replacement or qualification |
| --- | --- | --- |
| Lines 9, 50–58: complete HA fulfillment; data survival used as its definition | **Overstated** | Describe a live, recoverable single-primary demonstration deployment. It has one control-plane node and one database instance on that node. Explain interruption and operator recovery separately from data durability. Agree and demonstrate the availability objective before claiming literal HA completion. |
| Lines 9, 31, 57: complete raw-only rebuild proved every night | **Overstated** | There is a configured nightly drill and a recorded successful manual two-phase run. At the observed snapshot the scheduled run had failed; the later manual run succeeded. Its logical check compares eligible Silver-version fingerprints as a subset, permits extra rebuilt versions, excludes newer-than-replica data and does not compare current views. R5/R6 also limit multi-target and historical-derivation claims. |
| Lines 55–56: fixed maximum 15-minute loss | **Too absolute** | State intended RPO under successful archive/replication, including copy duration, scheduling delay and observed job health. The repository itself describes replica RPO as 15 minutes **plus copy time**. A cadence alone is not a maximum during job failure. No provider-loss experiment was conducted by this review. |
| Line 58: failed upgrade leaves everything untouched and costs no data | **Incorrect guarantee** | Atomic Helm release rollback does not reverse completed migration or application data writes. Describe the actual rollback-compatible migration policy and the separate invalidation/replay or restore procedure for data repair. The documented successful hook rollback demonstrations remain useful evidence, but do not establish a database transaction around an upgrade. |
| Line 100 and incident/monitoring discussion: rules actively watch operational health | **Not demonstrated for the live stack** | The exporter and rules are delivered. No evaluator/notification path is evidenced in the demo deployment, and required Kubernetes metrics are not evidenced there. Say alerting integration and end-to-end delivery verification are outstanding unless an external integration can be shown. |
| Lines 11, 169, 205: four unseen agents each produced a target; two empty-memory runs | **Inconsistent with the acceptance record** | Four trials passed the documented acceptance criteria: three adapter-path trials and one admission request; one adapter trial was CLI-only. `docs/09-acceptance-report.md` explicitly records global-memory contamination for the earlier trials and documents run 4 as the strict empty-profile rerun. This is still good evidence, but not four independent unseen-source adapters or two evidenced strict-profile trials. |
| Lines 11, 175–177, 199: every bad practice impossible or rejected before merge; universal agent authority restrictions | **Scope needs precision** | There are 71 named constraints implemented through a mixture of static/CI, runtime, deployment and procedural controls, not 71 distinct pre-merge proofs. Live main protection has 12 required checks and one approving code owner, with administrator enforcement disabled. The restricted MCP surface is not an OS sandbox for an arbitrary CLI agent holding maintainer credentials. Keep semantic golden review and the maintainer/agent credential boundary explicit. |
| Lines 9, 46 versus the cadence table: all seven datasets captured every 15 minutes | **Operationally misleading** | There are seven targets with different schedules; some share datasets. Three principal targets run every 15 minutes, the day-ahead target daily, the daily settlement target hourly and two settlement targets monthly. In the snapshot, the monthly capture jobs had not reached their first scheduled run. Distinguish implemented/fixture-tested targets from targets with live captured data. |
| Lines 62–66: one command and nothing created by hand | **Needs bootstrap qualification** | The infrastructure and application resources are substantially codified. Cloud accounts, credentials, repository variables, initial namespace secrets and state still require the documented owner setup. State this prerequisite rather than implying that a fresh reader with no credentials can reproduce the live account from one command. |
| Lines 207, 216: all 17 earlier findings fixed and closed | **Disposition is more nuanced** | The response record contains actual fixes, explicit limitations and deferred capabilities. Unsupported CNPG/external restore combinations now fail closed; that is useful protection, but does not implement their recovery path. Report findings as addressed by their stated dispositions, rather than implying all capability gaps became verified implementations. |

The Helm distinction follows both the repository's ADR-016 and the official [Helm hook lifecycle documentation](https://helm.sh/docs/topics/charts_hooks/): hooks run jobs during lifecycle stages, and their effects are not a transactional rollback of an external database.

## Proposed replacement for the opening conclusion

> We built and deployed a working platform for public Czech energy-data ingestion, with seven declarative targets, immutable raw storage, PostgreSQL history, reproducible infrastructure and a constrained contributor workflow. Fresh offline and PostgreSQL tests pass, and the live system is capturing and processing data. Contributor trials demonstrate both adding supported targets and escalating unadmitted sources. The current low-cost deployment provides durable copies and recovery machinery, but still has a single database/control-plane failure domain. Scheduling, release-aware replay, operational alerting and the full-history restore guarantee have specific remaining acceptance items described in the independent review.

After those items are resolved and verified, the conclusion can be strengthened with the resulting evidence. It should not be strengthened merely because a deployment is green or a roadmap phase is checked off.

The precise code findings and closure conditions are in [the deep review](01-deep-review.md); verification boundaries are in [the evidence record](03-verification.md).
