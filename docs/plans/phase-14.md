## Decisions

| # | Decision | Why |
|---|---|---|
| P14-D1 | **A receiver's credential comes from a Secret, never from values.** `alerting.alertmanager.existingSecret` (a name; empty by default) is mounted read-only at `/etc/alertmanager/secrets`, `optional: true`, every key a file; the operator's receiver values name those files with Alertmanager's own `*_file` fields (`auth_password_file`, `url_file`, `http_config.basic_auth.password_file`, `http_config.authorization.credentials_file`). The Alertmanager pod keeps `automountServiceAccountToken: false` and no platform environment. | The receivers render into a ConfigMap by `toYaml`; anything typed there is world-readable in the namespace and in Git. Alertmanager reads `*_file` at notification time, so the config loads before the Secret exists and the volume fills in when the author creates it (`optional: true`): the chart can name the Secret on the demo before the author has chosen the channel. A dedicated Secret rather than `secrets.existingSecret`: Alertmanager must not hold the platform's DSN or store keys (ADR-040 §1: the receiver side holds no credential). |
| P14-D2 | **Two refusals at render.** (a) A credential-bearing key inside `alerting.alertmanager.receivers` (`auth_password`, `auth_secret`, `password`, `credentials`, `bearer_token`, `api_key`, `api_secret`, `routing_key`, `service_key`, `token`, `secret`) fails the render with the `*_file` alternative named. (b) A route (at any depth) whose `receiver` is not `platform-sink` or a declared receiver fails the render. | (a) is the gate for D1: a value that would have landed in the ConfigMap never renders (`05` C-76). (b) Alertmanager refuses such a config at load, the pod never becomes ready, the upgrade gate rolls back — late, and with the reason three `kubectl` commands away; a render-time message names the route and the receiver (`05` C-77). |
| P14-D3 | **The interim night-time routing is a values example, not a rule change.** `ci/receiver-values.yaml` (rendered by the chart test) and the runbook show: child route 1 — `EnergyPlatformTargetLate` for `ote_dam` and `ote_imbalance_settlement` → `platform-sink` only (logged, never paged); child route 2 — `severity = page` → the operator's channel with `continue: true`; child route 3 — a catch-all → `platform-sink`, so the receiver's log stays the delivery record of every alert (ADR-040 §1). Pipeline, backup, replication and drill failures keep paging. | The freshness code documents that a day-ahead target's lateness is detected up to a day late and names a manifest-level expectation as the fix; the daily settlement's publication timing is `[UNVERIFIED]` (`01` §10). Until Phase 15 calibrates them, paging a person at 01:45 for those two is noise that teaches people to ignore the channel; silencing every alert at night, or widening `for:`, would hide the failures that matter. Routing is the operator's layer for exactly this. |
| P14-D4 | **The routing semantics are tested, not only the shape.** The chart test walks the rendered routing tree the way Alertmanager does (first matching child, `continue`, the parent's receiver only when no child matches; matchers `=`, `!=`, `=~`, `!~`) and asserts the receivers for four representative alerts: TargetLate on `ote_dam` → sink only; RestoreDrillFailed (page) → channel + sink; SourceUnavailable (warning) → sink only; TargetLate on `ceps_load` → channel + sink. | A `routes:` list that parses is not a routing that behaves; the mistake this guards against (a page alert reaching only the channel, or the night alert reaching the channel) is invisible in a structural assertion. |
| P14-D5 | **The runbook for the demo** (`docs/07` §7.3): create the Secret in the namespace, the values (receiver with `auth_password_file`, the three routes, `egress.cidrs` = the provider's published submission netblocks, `ports: [587]`), the checks (`amtool`-free: the rendered config through `helm template`, the receiver's log, the mailbox), and the two facts the advice omitted: Hetzner Cloud blocks outbound port 25 by default — use the authenticated submission port — and the egress rule is an IP block, so a provider behind rotating addresses needs its published netblocks (Google's are under `_spf.google.com`; the `dig` commands are in the runbook). The drill: the same failed Job as §7.2, then both messages (`firing`, `resolved`) in the mailbox. | The receiver proves delivery to a log; the brief's operator interface (A-6) is a person. The runbook is what turns the values change into a notified person, and it is the author's to run (Level 3). |
| P14-D6 | **The final report is committed** after an accuracy pass and states the commit it describes. Corrections: the failover demonstration is engineering plus cost (three servers with embedded etcd, a replicated PostgreSQL under an operator with its own backup chain, a measured node-loss drill), not "a cost decision rather than an engineering one"; delivery to a log is distinguished from notification of a person, with what this phase adds; the ČEPS series question is stated as recorded (`06` §4.2: equal on every quarter-hour and hourly item, different on the daily aggregate; both stored as published; no conclusion); the teardown separates the deploy workflow, the servers and the locked buckets (own-cluster README §6); the counts (phases, constraints, tests) are the repository's at that commit. | An evaluator needs a stable account tied to the implementation; an untracked file has no commit. The author reversed the earlier choice on 2026-09-25 ("yes commit the report"). |
