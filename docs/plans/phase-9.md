## Decisions

| # | Decision | Why |
|---|---|---|
| P9-D1 | **G1, without a server replacement.** `hcloud_server` (server and agents) gets `lifecycle { ignore_changes = [user_data] }`; the root exports the rendered `rbac_yaml` next to `authn_yaml`; a new `make demo-reconfigure` copies both over SSH to the paths cloud-init wrote (`/etc/rancher/k3s/authn.yaml`, `/var/lib/rancher/k3s/server/manifests/energy-platform-rbac.yaml`) and restarts k3s. Recorded as **ADR-035 amendment 1**. The authentication file gains a claim rule on `job_workflow_ref` (= `jalalhussein1982/energy-platform/.github/workflows/deploy-demo.yml@refs/heads/main`). The deployer `Role` drops `secrets`, `pods/exec` and `pods/portforward`; `deploy-tenant` stores Helm releases as ConfigMaps (`HELM_DRIVER=configmap`), and the demo's three release records are copied from Secrets to ConfigMaps once, by the admin. | The hcloud provider keeps only a hash of `user_data`: any template change otherwise replaces the server, which means a new k3s CA and datastore, a replaced agent, new repository variables and Secrets, and a Postgres restore (Phase 5 quirks). A pod-creating identity can still read the namespace's Secrets through a workload it creates. That is inherent to any deployer and is recorded as the residual. What goes is the direct `get secrets` and `exec` path. |
| P9-D2 | **G2:** a target's `auth.secretRef.name` must be `target-<target_id with - for _>` and its `key` alphanumeric (`manifest` layer, harness-check). At runtime the target's resolver is wrapped in `ScopedSecretResolver`, which refuses any other name. The environment variable becomes `TARGET_<ID>_<KEY>`. The platform's names (`BRONZE_*`, `POSTGRES_*`, `ENERGY_PLATFORM_*`) never start with `TARGET_`, and an alphanumeric key makes the last `_` the unambiguous id/key boundary. New `05` row C-62 and negative tests. | A manifest could name `{name: BRONZE, key: secret-access-key}`. With this rule it can no longer be written, and a crafted model bypassing validation still cannot resolve it. |
| P9-D3 | **G3:** fetch reads every response as a stream with a cap: `Fetcher(max_body_bytes=64 MiB)` by default. A `Content-Length` above the cap is refused before the body is read, and a streamed body that exceeds it is aborted. The error is `EgressError("response_too_large")`, which is not retried. Error bodies (5xx) are read to at most 2 KiB. New row C-63 and negative tests with a fake transport. | The largest committed payload is well under 2 MiB (an XLSX day, a SOAP month ≈ 1.9 MB). Of the defences named in threat-model item 2, only the pod memory limit remained. |
| P9-D4 | **G4:** `ci-bootstrap` downloads the pinned `uv-x86_64-unknown-linux-gnu.tar.gz` release asset, checks it against a SHA-256 pinned in the Makefile (the same pattern as `ci-terraform`), and unpacks `uv` into `~/.local/bin`. A harness test refuses `| sh` in any CI-reachable recipe. | Supply-chain parity with `ci-terraform`; threat-model items 3 and 9. |
| P9-D5 | **G5:** dispatch `weekly-drills` on `main` and fix each defect it finds as its own `fix(...)` commit, until it is green. Record the first green run in `07`. | The drill has never run on GitHub. |
| P9-D6 | **G6:** `deploy-demo` gains `push: branches [main]` with a paths filter (`energy_platform/**`, `targets/**`, `deployment/helm/**`, `deployment/tenant/**`, `deployment/image/**`, `pyproject.toml`, `uv.lock`, `Makefile`, the workflow itself), after G1 is live. The workflow test asserts the trigger set and the filter. | A merged target reaches the demo without a manual step. A docs-only push does not rebuild. |
| P9-D7 | **G7 (V-11):** in `hussein-ns`, a restricted-PSS scratch pod labelled `app=ep-v11-probe` and a NetworkPolicy that selects **only that label** (the namespace hosts the author's other workloads). The policy allows DNS and nothing else. `curl https://www.ote-cr.cz/en` must fail at connect; after the policy is deleted it must succeed; then everything is deleted. The entry goes in `00` §5 (the sanctioned log), and the result updates the roadmap Phase 5 box, the tenant README and threat model §6. No release (ADR-028). | Allowing DNS separates "egress blocked" from "name not resolved". Scoping the policy to one label leaves the namespace's other workloads untouched. |
| P9-D8 | **G8:** an honest **N-hour observation** from the demo's own history since 2026-09-23 06:30 UTC. Read-only SQL over `runs`/`run_attempts` and the capture log's `content_changed` transitions, per target, goes into `06` §6 as "observed, N hours, not a week". OTE's published settlement schedule is checked and the imbalance cadence justified or changed. `01` stays untouched; no figure is presented as a weekly latency. | The one-week campaign was closed without running. The demo has been polling since this morning. |
| P9-D9 | **G9 (F-4): a platform capability plus Route A targets.** Bounded reads today: version 1 (monthly) for 2026-08-31 is published; version 2 (final) exists for May 2026 and not for June. The lag is about 3–4 months, beyond ADR-033's 31-day correction window, and no placeholder can name an earlier month. **ADR-033 amendment 1** adds two strict render names, `month_start[k]` and `month_end[k]` (the first and last civil day of the month *k* months before the delivery day's month, 0 ≤ *k* ≤ 12). Then `ote_imbalance_settlement_monthly` (version 1: 1st of each month, previous month, correction 31 days) is built through the harness as a target-only PR, and the author merges it. Version 2 is the unseen source of the blind re-run (P9-D10). | "One more Route A target per version" (F-4) becomes true without a delivery-day offset, which ADR-033 rejected. The capability is platform code with tests; the targets stay declaration only. |
| P9-D10 | **G10 (F-3): the strictly blind re-run is a Route A run on settlement version 2** (final). Run 1's source now exists on `main`, so it is no longer unseen. The run uses Claude Code in a fresh clone in a new folder with an empty `CLAUDE_CONFIG_DIR` (no user memory, settings, plugins or skills) and `--strict-mcp-config` (no connectors), with run 1's prompt shape. The author runs it; the maintainer evaluates it into `docs/09` with the same independent checks as Phase 7. Because the author needs this early, 9.2 (the render capability) runs right after the plan, ahead of P1. | Blindness is guaranteed by the setup, not by the agent. Version 2 needs the new capability, so the run also tests whether the documentation is enough to find it. |
| P9-D11 | **P3 order by value per hour:** G17, G18, G16, G15, then G14, G12, G13. Anything not built goes into the README table with its reason. | Cheap closures first; G12 needs an admitted LLM host whose terms fit a commercial deliverable; G13 needs an ADR amending ADR-027. |
