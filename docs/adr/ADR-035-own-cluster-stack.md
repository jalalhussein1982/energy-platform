# ADR-035 — `own-cluster` stack: k3s on plain VMs by cloud-init, four Terraform modules, two roots

| | |
|---|---|
| Status | ACCEPTED |
| Date | 2026-09-22 |
| Resolves | D-1 (`02-architecture-decisions.md` §4.2) — the stack details ADR-028 left open; amends ADR-028 §2 (API port reachability for the OIDC deploy) |

## Context

D-1 chose "VMs + cloud-init k3s/RKE2" because Magnum is absent on the reference cloud (A-2, V-5)
and ADR-028 added a second, applied root on Hetzner. What is still undecided is everything a
coding agent needs to write the Terraform: which distribution, which k3s options, how the nodes
find each other, how the deploy identity of ADR-015 reaches the API server, and what the modules
export. V-14 supplied the facts that matter: k3s v1.36.4 accepts a `v1` `AuthenticationConfiguration`
trusting the GitHub Actions issuer, it does **not** set `anonymous-auth` when
`authentication-config` is given (so the file must say `anonymous.enabled: false`), `cx22` no
longer exists (`cx23` does), and `hcloud` has no Object Storage commands (buckets are managed over
S3). V-5 fixed the OpenStack quota (20 vCPU / 50 GB / 1 floating IP, `routers=0`, application
credentials). V-12/V-13 fixed the bucket controls (ADR-036).

## Decision

1. **Distribution: k3s, pinned.** One version string (`var.k3s_version`, default the V-14 version
   `v1.36.4+k3s1`) installed by the official installer with `INSTALL_K3S_VERSION`; the installer
   verifies the binary's SHA-256 against the release's checksum file. RKE2 is not used (Phase 5
   needs nothing RKE2 adds; k3s is the one already verified). Ubuntu 24.04 images on both clouds.

2. **Server configuration** (`/etc/rancher/k3s/config.yaml`, written by cloud-init from a
   template shared by both roots):
   - `disable: [traefik, servicelb]` — ingress is a values flag in `own-cluster`, never assumed;
   - `secrets-encryption: true`; `write-kubeconfig-mode: "0600"`; `tls-san` = the public address;
   - `node-ip` / `flannel-iface` on the **private** network; the embedded NetworkPolicy
     controller stays enabled (it is what enforces ADR-026 layer 1 here — nothing to install);
   - `kube-apiserver-arg: [authentication-config=/etc/rancher/k3s/authn.yaml]`;
   - `authn.yaml` = an `apiserver.config.k8s.io/v1` `AuthenticationConfiguration` with
     **`anonymous: {enabled: false}` written explicitly** (V-14), one JWT authenticator for
     `https://token.actions.githubusercontent.com`, audience `var.oidc_audience`
     (`energy-platform-demo`), username `'gha:' + claims.repository`, claim validation rules
     `claims.repository == var.github_repository` and `claims.ref == 'refs/heads/main'`;
   - `/var/lib/rancher/k3s/server/manifests/energy-platform-rbac.yaml` (auto-applied by k3s):
     namespace `energy-platform`, a `Role` with the verbs the chart needs on namespaced core and
     `batch`/`apps`/`networking.k8s.io` kinds, a `RoleBinding` to the user
     `gha:<github_repository>`. No `ClusterRole`, no `ClusterRoleBinding` for that user.
   - Agents join over the private network with a token generated by Terraform
     (`random_password`, marked sensitive, delivered only through the agents' user data).

3. **Four modules, one contract each** (`deployment/own-cluster/terraform/modules/`):

   | Module | Provides | Inputs it owns |
   |---|---|---|
   | `network` | private network + subnet; public entry address (Hetzner: server primary IP; OpenStack: the one floating IP) | CIDRs, region/zone |
   | `nodes` | one server + N agents from the cloud-init templates | server type, count, image, k3s version, OIDC inputs |
   | `storage` | the Postgres block volume; **bucket A** (versioning + Object Lock) over the `aws` provider pointed at the S3 endpoint; **bucket B** (retention rule, versioning disabled) over the `oci` provider — per ADR-036 | sizes, lock/retention days, endpoints |
   | `security` | firewall / security groups; SSH only from `var.admin_cidr` | admin CIDR, API CIDRs |

   Roots compose the modules: `roots/hcloud` (demo: 2 × `cx23` in `nbg1`, one 10 GB volume) and
   `roots/openstack` (reference: ≤ 3 × `e1.large`, pre-provisioned project network, one floating
   IP, `v3applicationcredential` variables; never applied). Both carry `tests/*.tftest.hcl` with
   `mock_provider` blocks; `make terraform-validate` runs `fmt -check`, `validate` and `test` for
   every root with `terraform` or, when absent, `tofu` (identical for these features).

4. **API port reachability (amends ADR-028 §2).** ADR-028 sized the firewall as "6443 from the
   author's address only". The ADR-015 federation clause deploys from GitHub-hosted runners,
   whose egress prefixes (several thousand, published at `api.github.com/meta`) exceed what a
   Hetzner firewall rule set can hold. Therefore `var.api_allowed_cidrs` defaults to the
   author's CIDR **plus** `0.0.0.0/0` when `var.deploy_from_github_actions = true` (the demo
   default), with the controls that make that acceptable: anonymous authentication off, no
   static token or basic auth, the only credentials being the admin client certificate (held by
   the author, never in CI) and short-lived OIDC tokens scoped to one namespace by RBAC, TLS on
   6443, and the hardening path recorded for production: a self-hosted runner inside the private
   network and `api_allowed_cidrs` back to the admin CIDR. 443/tcp stays open for a future ingress
   flag; 22/tcp and everything else only from `var.admin_cidr`.

5. **What the agent may do:** write every file above, `terraform plan -out` into
   `~/.config/energy-platform/plans/` (outside the repository, because a plan file embeds variable
   values), read state. `apply`, `destroy`, bucket deletion: the author (CLAUDE.md Level 3).

## Rationale

k3s is the distribution the probe used; every option above is either a V-14 fact or the
minimum that makes the tenant contract hold on a cluster we build (no Traefik so the chart never
depends on an ingress it did not declare; secrets encryption because the `Secret` is the default
D-7 backend). Splitting by module contract rather than by provider keeps ADR-001's "provider swap
= one module layer" promise measurable: the `hcloud` root and the `openstack` root differ only in
which provider each module instantiates. If the assumption "GitHub-hosted runners must reach the
API" turns out wrong (self-hosted runner accepted), point 4 collapses to ADR-028's original
sentence with one variable change.

## Rejected

- **RKE2** — CIS-hardened by default, but nothing in Phase 5 needs it and V-14 verified k3s; a
  second distribution to explain.
- **Magnum / OKE / any managed control plane** — rejected by D-1 and ADR-028; proves less of
  the Terraform path.
- **Terraform-managed kubeconfig via a long-lived token** — ADR-015 forbids agent-held
  credentials; the OIDC path is the one verified.
- **Allow-listing GitHub's published prefixes in the firewall** — too many for the provider's
  rule limits and they change; a control that silently breaks deploys.
- **Cilium/Calico on the demo cluster** — the embedded controller already enforces
  `NetworkPolicy`; `egress.fqdnPolicy` stays a values flag for operators who verified their CNI.
- **`curl | sh` without a pinned version** — the installer is used only with
  `INSTALL_K3S_VERSION` set, which makes it verify the release checksum.

## Consequences

- `02` §4.2 D-1 → "resolved by ADR-035"; the ADR index gains this row.
- `03` Phase 5 Terraform bullet: `cx22` → `cx23`; API CIDR wording per point 4.
- `deployment/own-cluster/README.md` carries the cost ceilings (ADR-028 §5) and the author's
  apply checklist; the plan output of the `hcloud` root is summarised in `docs/07-operations.md`.
- Devil's advocate: a single k3s server is a single control-plane point of failure (ADR-028
  already accepts it: the invariants are about data). Point 4 widens the API port's exposure;
  compensated by authentication and RBAC, and reversible by one variable.

## Amendment 1 (2026-09-23) — reconfigure without replacement; a narrower deploy identity

**Context.** Two residuals of `docs/threat-model.md` §14 sit in the files cloud-init writes. First,
the claim rules pin `repository` and `ref` only, so **any** workflow on `main` that asks for
`id-token: write` gets the deploy identity. Second, the deployer `Role` holds every verb on
namespace `secrets` (Helm's default driver stores its release records there) and `create` on
`pods/exec` and `pods/portforward`. Changing either file in the template changes the servers'
`user_data`. The `hcloud` provider keeps only a hash of it, so Terraform would **replace** the
server: a new k3s CA and datastore, the agent replaced as well (x509 unknown authority), the
repository variables and the namespace Secrets redone, and Postgres restored from backup (the
data lives on the volume, the k3s datastore does not). That is a disproportionate price for
two text files.

**Decision.**

1. **Cloud-init is first boot only.** Every `nodes` module's servers carry
   `lifecycle { ignore_changes = [user_data] }` (both clouds, one contract). The roots export
   the rendered `authn_yaml` and `rbac_yaml`. `make demo-reconfigure` reads both from the state,
   writes them over SSH (the admin key; port 22 is open to `admin_cidr` only) to the paths
   cloud-init used, keeps the previous authentication file as `authn.yaml.prev`, restarts k3s and
   waits for `/readyz`. k3s re-applies the RBAC manifest from its manifests directory. The mock
   tests still parse the rendered cloud-init, so a new node built from scratch gets the same
   files.
2. **The deploy identity is pinned to the deploy workflow.** A third claim rule:
   `claims.job_workflow_ref == '<repository>/.github/workflows/deploy-demo.yml@refs/heads/main'`.
   Another workflow on `main`, or the deploy workflow run from another ref, is refused with 401.
   `scripts/oidc_kube_context.sh` logs the claims the rules check (never the token).
3. **The deployer `Role` has no `secrets` verbs and no `pods/exec` or `pods/portforward`.**
   `deploy-tenant` runs Helm with `HELM_DRIVER=configmap` (`TENANT_HELM_DRIVER`), and the chart
   renders no Secret: the platform credentials and the pull secret are created by the operator
   (`secrets.existingSecret`, `image.pullSecrets`). An existing release is moved once with
   `make helm-driver-migrate` (an admin kubeconfig; it copies the records, checks `helm history`
   under the ConfigMap driver, and deletes the Secrets only with `DELETE_SECRETS=1`). An operator
   reading the release by hand sets `HELM_DRIVER=configmap` too.

**What remains (recorded, not hidden).** An identity that may create pods in a namespace can
read that namespace's Secrets through a pod it creates (a `secretKeyRef` or a mounted volume,
then its log). That holds for every deployer. What goes is the direct path (`get secrets`,
`exec` into a running pod) and the release records as a Secret-shaped target. The claim rules
still trust whatever reaches `main` in `deploy-demo.yml` itself, so code-owner review of
`.github/` stays the control (`CODEOWNERS`).

**Rejected.** Replacing the server to re-run cloud-init (see Context). A per-deploy short-lived
ServiceAccount token minted by an admin (a long-lived credential somewhere to mint it).
`pull_request_target` or environment protection rules as the pin (the environment `demo` exists
but carries no protection rule, and a rule on the workflow file is what the threat names).

**Verification (2026-09-23).** `terraform plan` after the change: resource changes none, outputs
only (applied). `make helm-driver-migrate`: revisions 1–3 readable under the ConfigMap driver.
`make demo-reconfigure`: pushed, k3s restarted, API ready in 16 s; the scheduled captures
continued. `kubectl auth can-i --as gha:jalalhussein1982/energy-platform`: `get secrets` no
(was yes), `create pods --subresource=exec` / `portforward` / `attach` no, the chart's verbs yes.
The first `deploy-demo` run after the change is recorded in `docs/07-operations.md` §4.1.
